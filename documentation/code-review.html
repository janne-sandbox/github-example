Offline DeepSeek code review

Execution model

The code-review.yaml workflow reviews Java and TypeScript on pushes to main and on manual dispatch. It targets a trusted self-hosted runner labelled code-review and ollama. Ollama must listen only on the runner at 127.0.0.1:11434, with deepseek-coder:6.7b installed unless DEEPSEEK_OLLAMA_MODEL selects another local model.

Verification boundary: GitHub-hosted runners cannot reach a developer workstation's loopback Ollama service. The workflow requires the offline model and fails if Ollama, the model, or a semantic response is unavailable or invalid.

Model verdicts are advisory and remain visible in the artifact and email. They do not fail the workflow by default because semantic findings require human validation. Local users may add --fail-on=denied when they intentionally accept model verdicts as a gate.

Review flow

flowchart LR P[Trusted push or manual dispatch] --> R[Self-hosted runner] R --> T[Node unit tests] T --> J[Java reviewer] T --> Y[TypeScript reviewer] J --> O[Local Ollama DeepSeek] Y --> O O --> A[Markdown artifact] A --> M{Recipient and OAuth credentials available?} M -->|No recipient| D[Workflow result without email] M -->|Yes| E[Resolve recipient and send with TLS plus XOAUTH2] E --> D

Recipient selection

For a push, the notifier checks the push payload email, head-commit author, checked-out commit author, and configured fallback in that order. A manual dispatch uses its selected fallback first. Invalid values, line breaks, GitHub noreply addresses, and addresses outside the optional domain allowlist are rejected.

Email contents and change context

PartCurrent content
Subject[owner/repository] code review: VERDICT
SummaryUTC timestamp, aggregate verdict, offline model name, and each reviewed language's verdict and report filename
DetailsComplete generated Java and TypeScript Markdown reports, separated by dividers
Delivery metadataThe source used to resolve the recipient, such as push payload, checked-out commit, or configured fallback
Size boundaryCombined report content is truncated after 200,000 characters before delivery
Current context limitation: the email does not include a PR/MR number, commit SHA, branch, pusher name, commit message, changed-file list, or GitHub Actions run URL. The review workflow runs on pushes to main and manual dispatches only; it does not currently run for pull-request events. GitHub uses the term pull request rather than merge request.

The Markdown artifact and email identify what the reviewers concluded, but recipients must currently use the repository and timestamp to correlate a message with a specific push. Adding immutable commit and workflow links is future work, not existing behavior.

Configuration

The workflow connects to smtp.gmail.com:465 with implicit TLS and authenticates as github-code-review@gmail.com using SASL XOAUTH2. Store the registered Google OAuth client ID and secret as SMTP_APPID and SMTP_SECRET.

Client credentials alone cannot authorize the Gmail mailbox. Authorize the Gmail user once with offline access and the https://mail.google.com/ scope, then store the consent-derived refresh token as SMTP_REFRESH_TOKEN. The notifier exchanges it for a short-lived access token at runtime. Never use or store the normal Google Account password.

The fallback address, allowed recipient domains, and local model remain repository variables. All three OAuth secrets are required for hosted Gmail delivery.

cd code-review npm test cd .. node code-review/run-review.js --languages=java,typescript --deepseek=true --internet=false --require-deepseek=true

Real Gmail delivery requires the client ID, client secret, refresh token, and a deliverable recipient. Local token-exchange and message-construction tests do not prove external delivery. Static HTML/link validation does not prove browser rendering; both evidence levels must be recorded separately.
