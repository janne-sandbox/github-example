CI quality gates

  • Maven compiles and runs backend tests on Java 21.
  • npm ci uses the committed lockfile on Node.js 26.
  • npm audit --audit-level=critical rejects critical advisories.
  • Vitest runs Angular unit tests and Angular creates a production bundle.
  • Backend JAR and frontend browser bundle are uploaded as build artifacts.

Azure deployment inputs

terraform/ provisions the resource group, ACR, AKS, monitoring, application-routing add-on, and environment-scoped GitHub OIDC identity. Its github_actions_variables output supplies the six Azure resource and identity values below without creating a client secret.

The manual AKS workflow uses GitHub environment variables rather than committed credentials:

AZURE_CLIENT_ID AZURE_TENANT_ID AZURE_SUBSCRIPTION_ID ACR_NAME AKS_RESOURCE_GROUP AKS_CLUSTER_NAME FRONTEND_PUBLIC_URL BACKEND_PUBLIC_URL BACKEND_PUBLIC_WS_URL
Verification boundary: workflow syntax and local artifacts can be checked without Azure access. A real deployment, image manifests, TLS, DNS, and AKS rollout require configured GitHub variables, federated identity, an ACR, and an AKS cluster.

Terraform workflow

cd terraform cp terraform.tfvars.example terraform.tfvars terraform init terraform validate terraform test terraform plan -out=github-example.tfplan terraform apply github-example.tfplan

Review the saved plan before applying because AKS, ACR, load-balancing, and monitoring resources incur Azure charges. Use the documented Azure Storage backend for shared state; never commit local state. Provisioning must run under an existing Azure identity allowed to create role assignments. After the first apply, copy the github_actions_variables output to the GitHub production environment and configure the three HTTPS/WSS public URLs.

Security boundaries

Workflows use GitHub OIDC for Azure login and never embed cloud credentials. Production frontend URLs must use HTTPS/WSS, and the backend CORS origin must match the deployed frontend exactly. The offline reviewer runs only for trusted main-branch pushes or manual dispatches because self-hosted runners and SMTP secrets must not be exposed to untrusted fork pull requests.

See Offline code review for the Ollama runner and SMTP configuration boundary.

Code-review notification boundary

The review email includes the aggregate and per-language verdicts plus the generated Java and TypeScript reports. Its subject identifies the repository and verdict. It currently omits pull-request ID, commit SHA, branch, actor, commit message, changed files, and workflow URL. See the linked offline-review page for the exact payload and 200,000-character report limit.
